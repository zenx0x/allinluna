# All in Luna - Run

This is the short execution entry. The ordinary user path is fixed:

```text
one-sentence request or existing plan
  -> one resource confirmation card
  -> Coordinator
  -> dependency waves
  -> result
```

Read [the ordinary user flow](references/user-flow.md) when the user needs the
mode table or retained compatibility paths. Do not make the newcomer learn the
run-state schema before starting.

## 1. Intake

Accept one sentence, existing conversation context, a local plan path, or a
complete third-party plan. Preserve the supplied direction and full completion
standard. A complete external plan is `parallel-only`; normalize only the
dependencies, ownership, resources, recovery, and dispatch needed to run it.

Use `$allinluna-plan` for an idea or incomplete plan. Do not create a Goal,
push, publish, deploy, or mutate an external service unless separately
authorized.

## 2. Confirm resources once

Present one resource card and ask once. The card selects `quick`, `standard`, or
`full`, plus optional `fast`, `ultra-fast`, `all-luna`, model/reasoning,
concurrency, Coordinator, and user-provided skills/plugins/MCP bindings.

- `quick`: Coordinator plus necessary Owner(s); no Integration/Acceptance by
  default.
- `standard`: multiple Owners when the dependency graph warrants them; one
  Integration only when a shared result actually needs it.
- `full`: explicit evidence/completion upgrade for high-risk, large
  cross-contract, or scientific-authority work; the lean runtime still does not
  materialize separate Acceptance/CounterPilot lanes.

These modes preserve scope. All in Luna does not default to multi-layer
governance, frequent interruptions, or a real canary on every run. See
[the user-flow reference](references/user-flow.md) for the complete card and
the exact retained compatibility promises.

## 3. Coordinate waves

Create the separate Coordinator before implementation Owners. The Coordinator
owns the DAG, releases ready conflict-free dependency waves, monitors Owners,
and returns product defects to their original Owner. The Sponsor remains the
human direction and authorization surface, not a hidden implementation lane.

Use the highest authorized delegation tier actually exposed by the host. Keep
requested, resolved, and actual model/tool/capability evidence separate, and
record `unavailable` when the host exposes no proof. Do not create micro-tasks
to fill concurrency or add control-plane roles not selected by the mode/risk.

## 4. Return the result

Complete every requested journey and failure path, not just the first slice or
first passing check. Return changed files/artifacts, checks actually run,
commit/worktree evidence when applicable, and exact blockers. Mechanical
Integration is risk-proportional, not automatic ceremony; legacy Acceptance and
CounterPilot fields remain metadata rather than runtime lanes.

## Non-negotiable boundaries

- A plan, dispatch, commit, or first vertical slice is progress, not completion.
- Goal creation, destructive operations, credentials, live external mutation,
  publication, and push require their own authorization.
- Acceptance is read-only and only exists when the selected risk boundary
  requires it; semantic defects return to the owning lane.
- User skills, plugins, MCP bindings, Research Routes, `fast`, `ultra-fast`,
  and `all-luna` remain supported through the routed references.
